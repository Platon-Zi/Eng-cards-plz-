## 1. Зафиксированные требования

1. Телефон показывает **слова, которые уже есть в системе** (ничего своего не добавляет).
2. На телефоне — только **2 большие кнопки**: 🔁 Practice (повторение) и 🌱 Learn New Words
   (заучивание). Как hero-кнопки дашборда (`#btn-hero-start-practice` / `#btn-hero-start-learn`).
3. Всё, что сделано на телефоне, **появляется на компе**; на телефоне видны актуальные цифры базы.
4. Словарь, статистика, добавление слов, группы, настройки — **только на компе**.
5. Метафора: **ПК = база (единственный мозг и хранилище), телефон = филиал (терминал)**.

## 3. Варианты (сравнение честное)

| | **A. Тонкий клиент по Wi-Fi** (рекомендация) | B. Полная копия на телефоне + merge | C. GitHub-облако (транспорт) |
|---|---|---|---|
| Как работает | ПК поднимает крошечный HTTP-сервер; телефон = пульт: кнопка → запрос → на ПК выполняется НАСТОЯЩИЙ `submitAnswer` | Телефон тянет всё состояние, сам считает очереди и ответы, пушит обратно, ПК сливает через merge | Состояние/события едут через приватный репозиторий GitHub |
| Комп должен быть включён | **да** (окно приложения открыто) | нет | нет |
| Работает вне дома | нет | частично (офлайн-сессии) | да |
| Интернет | не нужен (только Wi-Fi) | не нужен | обязателен + токен на телефоне |
| Дублирование правил SRS/§8 | **ноль** | высокое (порт `submitAnswer` в mobile.js) | среднее (см. этап 2 — event-log снимает) |
| Конфликты данных | **невозможны** (состояние одно, на базе) | MAX-merge может молча терять параллельный прогресс | возможны гонки записей |

| Объём работы | ~3–4 вечера | ~2–3 недели | поверх A: ещё ~1–2 недели |

Отвергнутое: Telegram-бот (UX карточек-переворотов не собрать, TTS нет), отдельное
приложение RN/Capacitor (дублирование всего), Syncthing/Dropbox (телефонный браузер не

только read-only дебаг, не участвует.

## 4. Рекомендация: этап 1 = вариант A (тонкий клиент)

Метафора пользователя реализуется буквально: **телефон — это экран и кнопки, база — всё
остальное**. Дополнительный бонус: во время телефонной сессии окно на компе показывает её
вживую (существующий `startTrainingSession` переключает экран на training) — механика
синхронизации «видима глазу», как принято в проекте.

### 4.1 Схема

```
┌───────── ТЕЛЕФОН (браузер/PWA) ─────────┐        ┌──────────── ПК: Electron ────────────┐
│  phone-sync/app/* (PWA, ~450 стр)       │  Wi-Fi │  phone-sync/server.js (~250 стр)     │
│                                          │ ─────► │   ↓ win.webContents.executeJavaScript │
│  🏠 2 кнопки: Practice / Learn           │  HTTP  │  phone-sync/bridge.js (7-й скрипт,   │
│  🃏 карточка: flip / Again / Hard / Easy  │  JSON  │   ~120 стр) = window.MobileSync      │
│  ↩ undo · ⏭ skip · 🔊 озвучка            │        │   ↓ вызывает НАСТОЯЩИЕ функции       │
└──────────────────────────────────────────┘        │  startTrainingSession / submitAnswer │
                                                    │   → srs.js → saveData → data/*.json  │
                                                    │  (весь существующий путь, без правок)│
                                                    └──────────────────────────────────────┘
```

### 4.2 Протокол (все `/api/*` требуют заголовок `X-Sync-Token`)

| Метод | Путь | Что делает на базе | Ответ |
|---|---|---|---|
| GET | `/` + статика | отдаёт только `mobile/*` (десктопный index.html в сеть НЕ отдаётся никогда) | PWA-оболочка |
| GET | `/api/overview` | читает живое состояние рендерера | `{due, bank, goal, learnedToday, streak, today, baseName}` |
| POST | `/api/session/start` `{mode:'learn'\|'system'}` | `startTrainingSession(mode)` (существующая, со всеми тостами) | первая карточка |
| POST | `/api/session/answer` `{answer:'again'\|'hard'\|'easy', hintUsed?}` | `await submitAnswer(...)` — guards, §8, streak, requeue, сохранение | след. карточка + последний тост |
| POST | `/api/session/undo` | `undoPreviousCard()` | карточка + счётчик |
| POST | `/api/session/skip` | обработчик `#btn-skip-card` → `SRS.sessionSkip` | след. карточка |
| POST | `/api/session/exit` | выход из сессии (как Escape) | `{ok}` |

Payload карточки ~0.5 КБ: word, phonetic, translation, example(+перевод), direction,
текст task prompt, уровень/чипы, счётчик `i / N (+M repeats)`, mode title. Flip и hint —
локально на телефоне (бэк уже в payload); hint помечает ответ как AGAIN при отправке
(та же семантика, что `hintUsedForCurrentCard`).

### 4.3 Мост и почему он именно script-тег

`main.js` не может дотянуться до внутренностей app.js напрямую. Решение —
**`phone-sync/bridge.js`, 7-й классический скрипт после `app.js`**: он живёт в том же глобальном
лексическом скоупе, читает `let`-глобалы (`appState`, `srsSession`, `currentTrainingItem`,
`currentTrainingQueue`) и зовёт function-глобалы (`startTrainingSession`, `submitAnswer`,
`undoPreviousCard`), а наружу отдаёт единственную точку входа `window.MobileSync = {overview,
start, answer, undo, skip, exit, currentCardPayload}`. HTTP-обработчик main'а вызывает
только его: `await win.webContents.executeJavaScript('window.MobileSync.answer("easy")')`.
Тосты для телефона: мост оборачивает `showToast` через вызов оригинала (поведение на компе
не меняется), последний текст кладётся в ответ `answer`.

⚠ Стоимость: 7-й скрипт = ритуал по контракту (обновить порядок в `index.html`, ожидания
`check.cjs`/`verify_ui.cjs`, `check:syntax` в package.json — процедура описана в AI-CONTEXT §3).

### 4.4 Сопряжение и безопасность

- Токен: 64 hex (`crypto.randomBytes`) в `userData/eng_cards_sync_token.txt`, генерируется
  при первом запуске. Все `/api/*` без верного токена → 403 + троттлинг подбора.
- Телефон подключается один раз: открывает URL с `#t=<token>` (фрагмент не летает в логах
  серверов), страница сохраняет токен в свой localStorage. Дальше — просто иконка на экране.
- Панель **«📱 Phone sync»** на экране Data & Backup (datacare.js): статус сервера
  (порт/ON-OFF), URL + кнопка Copy, «телефон подключён/отвечает», toggle. Кнопка ON —
  осознанное исключение из «100% Offline», подпись честная: «Local network only».
- HTTPS на домашнем Wi-Fi не разворачиваем (самоподпис = красные экраны на телефоне):
  WPA2-сеть + токен — соразмерно личным флеш-карточкам. Публичный Wi-Fi — не подключаться.
- Windows один раз спросит файрвол «Разрешить в частных сетях» — Разрешить.
- Порт: 8675 по умолчанию, автоперебор при занятости.

### 4.5 PWA-установка на телефон

`phone-sync/app/manifest.webmanifest` + минималистический service worker (кэш оболочки ~20 строк,
данные НЕ кэшируются — филиал без базы не врёт) + иконки 192/512 (новый генератор
`phone-sync/make_icons.cjs`; существующий `scripts/make_icon.cjs` не трогаем).
Android: «Установить приложение». iOS: Поделиться → «На экран “Домой”». Озвучка 🔊 — Web
Speech API, тап по кнопке = user gesture (iOS-требование выполнено).

### 4.6 Ограничения этапа 1 (говорим честно)

1. **Комп включён, приложение открыто** (`window-all-closed` → quit; позже можно
   minimize-to-tray, чтобы сервер жил при закрытом окне — этап 1.5).
2. Телефон и комп **в одной Wi-Fi** сети.
3. Одна глобальная сессия: старт с телефона **забирает** сессию (это тот же человек —
   фича, не баг: бросил на компе, продолжил с дивана). Двойная оценка одной записи
   невозможна (guard `sessionIsGraded` уже в ядре). Одновременный клик на обоих —
   последний выигрывает.
4. Если на компе открыт edit-modal — удалённый старт вежливо отклоняется (edge-кейс).
5. Потеря связи посреди сессии: ответ «не считается», кнопка уходит в retry — тонкий
   клиент не может знать исход, и это честно; прогресс не теряется (не отправленное = не
   сделанное).

## 5. Этап 2 (потом, отдельным решением): «комп выключен»

GitHub-транспорт поверх той же идеи: телефон тянет состояние из приватного репозитория,
**очередь строит чистыми функциями `srs.js`** (build*Queue — pure, им можно доверять), а
вот ответы НЕ применяет сам, а пишет в **лог событий** `{cardId, direction, answer, day}`.
База при появлении связи **проигрывает лог через настоящий `submitAnswer`-путь** — правила
по-прежнему в одном месте. Транспорт: GitHub Contents API (токен Contents:RW), событие ~
50 байт. Телефон остаётся «филиалом»: без базы он может тренироваться, но решения
(уровни, due, streak) принимает только база при синке. Гонки решаются таймстампом
`saved_at` + идемпотентностью проигрывания. Делать только если «повторение в дороге без
компа» станет реальной потребностью.

## 7. Сложность / надёжность / опасность — честная оценка (22.09, вопрос пользователя)

**Сложность: низкая-средняя (3–4 вечера).** ~1100 строк нового кода, из них 90% — новые
файлы (сервер, мост, мобильная PWA, тесты); существующие файлы получают суммарно ~100
строк, а ядро `srs.js` и путь записи данных — **ноль изменений**. Три рифа:
(1) ритуал 7-го скрипта — порядок в index.html + ожидания check.cjs/verify_ui/check:syntax +
jsdom-склейка: процедура известная, забыть нельзя — verify покраснеет;
(2) сериализация async-ответа (`submitAnswer` ждёт `saveData`; `executeJavaScript`
резолвится вместе с promise — проверяется первым же тестом);
(3) зоопарк мобильных браузеров (iOS-жесты для озвучки, установка PWA) — тестируется
только руками с телефона. Исследовательских неизвестных нет: стандартный веб, ноль зависимостей.

**Надёжность: высокая — по построению.** Мозг один (рендерер), путь записи один
(`validateState` → атомарный write+fsync+rename → readback). Телефон физически не может
испортить базу: он отправляет только enum-ответы `{'again','hard','easy'}` в настоящие
функции. Конфликтов синхронизации не существует, потому что состояние одно. Отказы
деградируют честно: Wi-Fi упал → ответ «не считается», кнопка retry; комп закрылся → то же;
на диске всегда консистентно (атомарные записи). Откат: toggle OFF в панели или git revert —
формат данных не меняется, миграций нет. Даты считает только база (`srsToday` в рендерере) —
расхождение часов телефона вообще не участвует.

**Опасность: низкая при ДВУХ железных правилах** — это единственные реальные дыры, обе
классические, обе закрываются тестами:
1. **Инъекция в executeJavaScript.** Ответ телефона попадает в строку JS, а рендерер живёт
   с `nodeIntegration:true` ⇒ инъекция = RCE. Правило: сервер валидирует mode/answer по
   ЖЁСТКОМУ enum-белому списку ДО построения строки; никакой другой пользовательский текст
   в executeJavaScript не попадает никогда.
2. **Path traversal в статике.** `GET /../../data/leitner_data.json` не должен отдаваться.
   Правило: белый список КОНКРЕТНЫХ файлов mobile/* (allowlist, не «санитизация»).

Прочее (мелочи, зафиксированы): POST-тело ≤4 КБ; CORS-заголовков нет ⇒ кросс-сайтный запрос
с токеном в заголовке невозможен (CSRF заблокирован); токен 256-бит + 403/троттлинг на
подбор; **дампа базы через API этапа 1 не существует** (только счётчики overview + карточки
живой сессии) — слить весь словарь нельзя даже с токеном; plain HTTP в домашнем WPA2
теоретически снифается (видны тренируемые карточки) — для личных флеш-карточек принято,
публичный Wi-Fi исключён; AP-isolation роутера / VPN на телефоне = «база не найдена»
(лечится настройками сети); IP компа сменился (DHCP) → перекопировать URL, 30 секунд.
Worst case с украденным токеном (нужен физический доступ к разблокированному телефону):
кто-то поучит твои слова — данные не теряются, уровень сдвинется. ОС-нотификация про
файрвол на Windows — один раз «Разрешить», на Linux нет.

Сравнение с альтернативами: «толстый» телефон (вариант B) опаснее — кривой merge портит
базу, а история проекта полна именно merge/restore-багов; облако — токен наружу +
интернет-поверхность. Тонкий LAN-клиент — минимальная поверхность из возможных.

## 8. Итог

- **Рекомендация (22.09, вопрос «делать или нафиг»): ДЕЛАТЬ этап 1.** Аргумент: это фича
  с максимальным рычагом на реальную цель проекта (выучить язык) при минимальной цене и
  полностью откатываемая. Единственный сценарий «не надо»: если тренировки реально будут
  происходить ВНЕ дома при выключенном компе — тогда сначала этап 2 (GitHub), но этап 1
  остаётся его фундаментом и не пропадает.

- **Возможно — да.** Этап 1 (тонкий клиент по Wi-Fi) даёт ровно запрошенное: 2 кнопки,
  слова из системы, двусторонняя синхронизация моментально и без конфликтов.
- Цена этапа 1: комп должен быть включён; этап 2 (GitHub-лог событий) снимает и это, если
  понадобится.
- Ключевая архитектурная находка: телефону не нужен «второй мозг» — он вызывает
  существующие `startTrainingSession`/`submitAnswer` на базе. Правила SRS живут в одном
  месте, как и сейчас.
